Guía de Laboratorio: Seguridad en
Autenticación Web
Tema: Autenticación Segura, Hashing de Contraseñas y Protección contra Fuerza Bruta
Objetivo General
Diseñar e implementar un sistema de autenticación seguro para una aplicación web, aplicando
técnicas modernas de hashing de contraseñas mediante algoritmos con salt automático (BCrypt) y
desarrollando mecanismos de defensa perimetral en el servidor mediante alguna método escogido
previamente, para mitigar ataques de fuerza bruta.
Introducción Teórica y Nota Arquitectónica
Importante
Antes de iniciar con los componentes del laboratorio, es fundamental establecer una premisa clave
de la arquitectura de seguridad web:
Nota Arquitectónica Obligatoria: Toda la lógica de autenticación, verificación de credenciales,
hashing de contraseñas y control de intentos fallidos debe procesarse exclusivamente en el lado
del servidor (backend) utilizando lenguajes y frameworks como Node.js (Express), PHP (Laravel),
Python (Django/FastAPI) o Java (Spring Boot). Los lenguajes del lado del cliente como HTML, CSS y
JavaScript ejecutado en el navegador no son seguros para este propósito, ya que el código fuente
puede ser inspeccionado, modificado o ignorado completamente por un atacante a través de las
herramientas de desarrollo del navegador o mediante solicitudes HTTP directas.
El proceso de autenticación segura involucra los siguientes principios teóricos fundamentalmente
distintivos:
● Hashing Unidireccional: A diferencia del cifrado simétrico (como Blowfish o AES) que permite
recuperar el texto claro mediante una clave, una función hash criptográfica es una función
matemática de una sola vía. Una vez generada la cadena hash, es computacionalmente
inviable revertirla para obtener la contraseña original.
● Salt: Consiste en concatenar una secuencia aleatoria y única de caracteres a la contraseña de
cada usuario antes de aplicarle el algoritmo de hash. Esto garantiza que dos usuarios con la
misma contraseña generen hashes totalmente diferentes, anulando el uso de tablas arcoíris
(Rainbow Tables) y ataques de diccionario masivos precomputados.

Sección 2: Implementación de Hashing de
Contraseñas con BCrypt
2.1. Anatomía del Algoritmo BCrypt y Manejo Integrado del Salt
BCrypt se basa en el cifrado de bloques EksBlowfishSetup (Expensive Key Schedule Blowfish). Una
de las ventajas principales de BCrypt es que embebe automáticamente el costo computacional
(factor de trabajo) y el salt dentro del texto final generado. Una cadena hash típica de BCrypt luce
de la siguiente manera:
$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
\__/ \/ \____________________/\____________________________/
Alg Costo Salt (22 chars) Hash (31 chars)
● $2b$: Identificador de la revisión del algoritmo BCrypt.
● $10$: Factor de costo (2^10 = 1,024 rondas de iteración).
● N9qo8uLOickgx2ZMRZoMye: Salt único de 128 bits codificado en Base64.

Al momento de autenticar un usuario, no se requiere almacenar el salt en una columna separada.
La librería del servidor lee la cadena almacenada en password_hash, extrae automáticamente el salt
y el factor de costo, procesa la contraseña ingresada por el usuario con esos mismos parámetros y
compara si ambos hashes coinciden de forma transparente.

Sección 3: Protección contra Ataques de Fuerza
Bruta mediante Middleware
Un ataque de fuerza bruta intenta adivinar contraseñas mediante pruebas automatizadas
repetitivas. Para mitigar esta amenaza, el servidor debe interceptar las solicitudes entrantes
utilizando un modulo intermedio o middleware
3.1. Concepto y Funcionamiento del Middleware
Un Middleware es una capa de código intermedio que se ejecuta antes de que una solicitud HTTP
alcance el controlador principal de la ruta de login. Evalúa metadatos como la dirección IP origen o
la tasa de peticiones y decide si permite continuar el procesamiento o bloquea la conexión
inmediatamente.
3.2. Estrategias de Bloqueo Implementadas
1. Limitación de Tasa (Rate Limiting) por IP: Registrar el número de peticiones enviadas desde
una dirección IP hacia la ruta /login en una ventana de tiempo determinada (ejemplo:
máximo 5 intentos cada 15 minutos).
2. Bloqueo Temporal y Retardo (Cooldown): Si se supera el número máximo de fallos
permitidos, la dirección IP se registra en una lista de bloqueo temporal (o en una memoria
caché como Redis / Map en memoria), devolviendo un código de estado HTTP 429 Too Many
Requests.
